== Systemübersicht & Hexagonale Architektur (Ports & Adapters)

_Dieser Abschnitt beschreibt die hexagonale Struktur unseres PWA-Clients. Um die Geschäftslogik (Berechnung von Erfolgsketten, Recovery-Modus) vollständig von externen Frameworks und dem Backend-as-a-Service (Supabase) zu entkoppeln, wird das System in einen framework-freien *Fachlichen Kern* (Domain Core), abstrakte Schnittstellen (*Ports*) und technische Implementierungen (*Adapter*) aufgeteilt._

=== Beschreibung der Architekturbereiche

[cols="1,2,2", options="header"]
|===
| Bereich | Verantwortung | Darf abhängen von

| *Driving Adapters* (Inbound)
| Nimmt Benutzerinteraktionen aus der Vue-Oberfläche entgegen, verwaltet den reaktiven App-Zustand in Pinia und stößt fachliche Use Cases über die Inbound-Ports an.
| Inbound Ports, Domänen-Models

| *Inbound Ports* (API)
| Definiert die Einstiegspunkte und ausführbaren Anwendungsfälle (Use Cases) des Systems als abstrakte TypeScript-Interfaces.
| Domänen-Models

| *Fachlicher Kern* (Domain)
| Enthält die reinen Datenstrukturen (`Gewohnheit`, `Ausführung`) und die verhaltenspsychologische Logik. Vollständig isoliert von Datenbank- und UI-Bibliotheken.
| Keine äußeren Schichten (Absolut unabhängig)

| *Outbound Ports* (SPI)
| Definiert die Anforderungen der Domäne an die Infrastruktur (z. B. Datenspeicherung) in Form von Interfaces (z. B. `HabitRepository`).
| Domänen-Models

| *Driven Adapters* (Outbound)
| Implementiert die Outbound-Ports. Enthält den konkreten Code für die Verbindung zu Supabase (PostgREST) sowie das lokale Caching in der Browser-Datenbank (`IndexedDB`).
| Outbound Ports, Domänen-Models
|===

NOTE: Klassen innerhalb des *Fachlichen Kerns* dürfen zu keinem Zeitpunkt Frameworks wie Vue oder das Supabase-SDK importieren. Diese strikte Entkopplung stellt sicher, dass die Kernlogik in isolierten Unit-Tests validiert und die Infrastruktur bei Bedarf ausgetauscht werden kann.

=== Ausführung protokollieren (Offline-Fall mit lokalem Cache)

_Dieser Fluss zeigt, wie das System reagiert, wenn der Nutzer sich in einem Funkloch befindet (z. B. Hörsaal/Bibliothekskeller). Das UI bleibt dank der Offline-First-Architektur blockierungsfrei._

[plantuml, sequence-logging-offline, svg]
....
@startuml
skinparam monochrome true
skinparam defaultFontSize 12

actor "Nutzer:in" as user
participant "Dashboard UI\n(Vue 3)" as ui
participant "Habit Store\n(Pinia / Driving)" as store
participant "Domain Core\n(TypeScript / Kern)" as domain
participant "Supabase Adapter\n(Infrastruktur / Driven)" as adapter
database "IndexedDB\n(Lokaler Cache)" as cache
database "PostgreSQL\n(Supabase DB)" as db

user -> ui : Klickt "Erledigt" auf Gewohnheit
ui -> store : loggeAusfuehrung(gewohnheitId)
store -> domain : berechneErfolgskette(gewohnheit, neueAusfuehrung)
domain --> store : aktualisierteErfolgskette
store -> adapter : speichereAusfuehrung(neueAusfuehrung)
activate adapter
adapter -> db : INSERT INTO ausfuehrung ... (Netzwerkaufruf)
note over adapter, db : Netzwerkfehler / Zeitüberschreitung (Offline)
db --X adapter : Verbindung gegenwärtig fehlgeschlagen
adapter -> cache : speichereLokal(ausfuehrung, status='pending_sync')
cache --> adapter : OK
adapter --> store : Lokal gespeichert (Offline-Modus aktiv)
deactivate adapter
store --> ui : Zustand reaktiv aktualisiert (Offline-Indikator)
ui --> user : Zeigt Erfolg lokal an (Kein Lade-Spinner)

@enduml
....

=== Tabellenbeschreibung

[cols="1,1,3", options="header"]
|===
| Tabelle | Spalte | Beschreibung & Besonderheiten

.3+| nutzer
| id | UUID als Primärschlüssel; wird automatisch über Supabase Auth (Schema `auth.users`) generiert.
| email | Eindeutige E-Mail-Adresse für das Login-Verfahren.
| encrypted_password | Mit `bcrypt` gesichertes Passwort auf der Datenbank-Ebene.

.6+| gewohnheit
| id | UUID als Primärschlüssel.
| nutzer_id | Fremdschlüssel auf den Besitzer; RLS-Policy greift hierüber: `auth.uid() == nutzer_id`.
| name / beschreibung | Textbezeichner der Gewohnheit sowie optionale Ausführungsdetails.
| haeufigkeit | Speicherwert für Intervalle (z. B. `DAILY`, `WEEKLY`).
| aktuelle_erfolgskette | Zwischengespeicherter Integer-Wert zur performanten Abfrage im UI ohne Live-Neuberechnung.

.3+| ausfuehrung
| id | UUID als Primärschlüssel.
| gewohnheit_id | Fremdschlüssel auf die zugehörige Gewohnheit. Kaskadierendes Löschen (`ON DELETE CASCADE`).
| datum / status | Exakter Erfassungszeitpunkt; Status-Enum: `ERLEDIGT`, `VERPASST`.

.4+| tagebucheintrag
| id | UUID als Primärschlüssel.
| nutzer_id | Fremdschlüssel zur filterbasierten RLS-Absicherung des Tagebuchs.
| text / stimmung | Freitext zur Reflexion; Stimmungswert (Skala 1–5) für spätere Trendanalysen.
|===

=== Datenbankmigrationen

_Schemaänderungen werden im Supabase-Infrastruktur-Setup über versionierte SQL-Migrationsdateien innerhalb der Supabase CLI verwaltet, um eine identische lokale Docker-Entwicklungsumgebung zu gewährleisten._

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Werkzeug
| Supabase CLI (Migrations-Engine basierend auf nativen PostgreSQL-Skripten)

| Speicherort
| `/supabase/migrations/`

| Namenskonvention
| `<timestamp>_initial_schema.sql`, `<timestamp>_add_recovery_mode.sql`

| Regel
| Einmal auf die Remote-Infrastruktur gepushte Migrationsskripte sind unveränderlich (Immutable). Korrekturen erfolgen ausschließlich über neue Migrationsdateien.
|===

== Eingesetzte Muster & Konventionen

_Dieser Abschnitt dokumentiert übergreifende Designmuster und Konventionen, die in der Codebasis gelten, um die Wartbarkeit des Systems sicherzustellen._

=== Designmuster

[cols="1,2,2", options="header"]
|===
| Muster | Wo eingesetzt | Begründung

| Ports & Adapters (Hexagonal)
| Client-Architektur (`/src/domain` vs. `/src/infrastructure`)
| Entkopplung der Kernlogik von Supabase; nahtlose Integration des Offline-Caches (`IndexedDB`).

| State Management Pattern
| Pinia-Stores (`/src/stores`)
| Zentralisiert den veränderlichen Zustand der App; stellt sicher, dass alle Vue-Komponenten synchron auf Datenänderungen reagieren.

| Data Mapper Pattern
| Infrastruktur-Adapter (`/src/infrastructure/mappers`)
| Übersetzt flache Datenbankzeilen (PostgreSQL DTOs) in reiche, objektorientierte Domänenmodelle der TypeScript-Schicht.
|===

=== Fehlerbehandlung & Offline-Konflikte

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| Fachliche Fehler
| Werden im Domain-Core über dedizierte TypeScript-Fehlerklassen abgebildet (z. B. `UngueltigesIntervallException`, `PhaseUeberschneidungException`).

| Offline-Abfangung
| Tritt beim Aufruf des Supabase-Clients ein Netzwerkfehler ein, fängt der Infrastruktur-Adapter diesen geräuschlos ab, speichert die Daten in der `IndexedDB` und setzt die App in den Offline-Modus.

| Synchronisationskonflikte
| Bei der Wiederkehr des Netzwerks greift für den MVP-Stand eine deterministische **Last-Write-Wins (LWW)**-Strategie. Der aktuellere lokale Timestamp überschreibt bei Konflikten den Remote-Stand.
|===

=== API & WebSocket-Konventionen

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| Datenabfragen
| Erfolgen über das PostgREST-Interface des Supabase-SDKs. Abfragen sind durch RLS-Regeln implizit auf den authentifizierten Nutzer eingeschränkt.

| Echtzeit-Updates
| Für Live-Visualisierungen (z. B. sofortige Synchronisation zwischen Desktop-Browser und Smartphone) wird der Supabase-Realtime-Kanal via WebSockets abonniert.

| Datumsformat
| Einheitlich im ISO-8601-Format mit Zeitzone (`YYYY-MM-DDTHH:mm:ssZ`), um fehlerfreie Berechnungen der Erfolgsketten über Zeitzorengrenzen hinweg zu garantieren.
|===
